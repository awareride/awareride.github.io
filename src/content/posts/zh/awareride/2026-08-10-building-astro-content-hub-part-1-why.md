## 我真正面对的问题

我正准备启动一个开源组织。和大多数刚开始的人一样，我需要一个让组织能够"落地"的地方——一个介绍我们是谁、在做什么的主页。但我也清楚，这个组织下的每个项目都需要自己的文档和产品介绍页。

一开始，这些介绍页分散在各个独立的 GitHub Pages 站点里，一个项目一个。很快就很乱：

- 同一个组织的产品被拆散在 N 个不同的 URL 上。
- 每个项目都得从零解决"我怎么发布一个像样的页面？"这个问题。
- 没有统一的身份、统一的搜索、统一的本地化方案。

于是我给组织建了一个单独的 `site` 仓库，让其他项目把自己的 `docs/` 自动同步进来。忽然之间，组织里所有产品都聚到了一处，而这个站点的核心也变成了**组织与产品的介绍**——文档只是其中的一部分。

这个站点运转得足够好，让我开始问一个不同的问题：*如果别人也需要这个呢？*

## 从"我的站点"到"一套模板"的跨越

这个领悟很简单，却很重要。大多数小团队和独立开源作者都会撞上和我一模一样的墙：

> 我希望我的项目有一个体面的公开门面——文档、文章、产品页——而不必每个项目都重新造轮子。

于是我把那个组织站点**抽象成了一套名叫 `astro-content-hub` 的模板**。思维方式的转变是：

- **之前：**"这是*我的*站点，带着*我的*品牌和*我的*产品。"
- **之后：**"这是一个中性的骨架。填上你的品牌和产品，你就得到一个能用的 hub。每个外部项目只需聚焦自己的业务、顺手写点文档——就能免费获得一个体面的公开页面。"

这就是全部的"为什么"。我不是想再做一个文档框架，而是想给一个多仓库的组织一个内容家园，它要能：

1. **聚合** 来自许多仓库的文档与文章到一个站点。
2. **治理** 内容——通过 Pull Request，没有任何内容能在未经 review 的情况下登上 `main`。
3. **本地化** 采用逐页回退，缺翻译时绝不 404。
4. **免费部署** 到 GitHub Pages 和 Cloudflare Pages。
5. **保持可升级**，让使用者不会被 fork 时的版本锁死。

## 这里的"内容 hub"是什么意思

我最终落到的一句话是：

> *一个 hub，多个源仓库。*外部项目撰写 `posts/` 与 `docs/`。一个 GitHub Action 校验内容并开一个 PR。由人来 review。hub 构建并部署。

有三个想法让这句话真正成立，值得单独点出来，因为它们塑造了之后的一切：

- **内容通过 PR 流动，而非 push。** 每一次外部贡献在上线前都由人 review。这是它与"构建时自动拉取"类聚合器最大的区别。
- **产品是数据，不是文件。** 你在 `site.config.ts` 里用一行注册一个产品，路由、侧边栏、卡片、导航就都从那里生成。
- **模板是分层的。** Machinery（引擎）、Your site（你的品牌与内容）、Extensions（可选钩子）被刻意分开——这样日后升级不会变成一场巨大的冲突。
